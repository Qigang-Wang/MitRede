# 技术方案分析

## 1. 技术结论

建议首版采用“TypeScript 单语言的前后端分离模块化单体 + 独立后台任务进程”，在所内以 Docker Compose 部署。具体技术选型及决策理由以[技术选型决策](./technology-decision.md)为准：

```text
浏览器（编辑端 / 主持端 / 参与端）
                  │ HTTPS / WebSocket
                  ▼
              Nginx 入口
              ├── React 前端静态资源
              └── NestJS 应用
                    ├── PostgreSQL / Prisma
                    ├── Redis / Socket.IO
                    ├── 对象存储
                    └── BullMQ Worker ── PDF处理 / AI调用 / 导出
```

推荐技术组成：

- 前端：React + TypeScript + Vite。
- 后端：TypeScript + NestJS。
- 数据库：PostgreSQL。
- 数据访问：Prisma，并保留事务和原生 SQL 能力。
- 实时通信：Socket.IO，使用 WebSocket 并保留轮询降级。
- 缓存与跨实例消息：Redis；多实例时采用 Socket.IO Redis Streams Adapter。
- 文件：首版可用挂载卷，正式部署推荐 S3 兼容对象存储，如所内 MinIO。
- PDF：前端 PDF.js 作为预览/降级，后台 Worker 调用 MuPDF 或 Poppler 生成页面图和缩略图。
- 后台任务：BullMQ + 独立 Worker，负责 PDF、AI 和导出任务。
- 部署：Docker Compose + Nginx；规模和运维条件没有明确要求前不采用 Kubernetes。

这一组合的重点不是追求技术新颖，而是让前端、后端、实时事件和 Worker 统一使用 TypeScript，以编译器和共享契约约束 AI 生成代码；同时让 PDF 处理、实时房间、AI 任务和普通业务数据保持清楚边界。

## 2. 为什么不建议首版采用其他形态

### 2.1 不建议微服务

所内工具的团队和流量通常不足以抵消微服务带来的服务发现、分布式追踪、网络错误、部署编排和数据一致性成本。代码内部按模块划分，后台任务独立进程，已经能隔离主要风险。将来某一模块出现明确扩容需求时再拆分。

### 2.2 不建议只用无状态 HTTP

主持翻页、参与端跟随和结果实时更新都需要服务器主动推送。纯轮询会制造额外请求，并让延迟与服务器负载相互牵制。WebSocket 更适合作为主通道，但必须保留重连和快照机制，不能把连接本身当成可靠消息队列。

### 2.3 不建议把所有状态只放在 Redis

Redis 适合活跃房间、在线计数和广播，但最终场次、答案和审核状态需要持久保存。PostgreSQL 是事实来源，Redis 是加速层。即使 Redis 丢失，系统也应能从数据库恢复场次关键状态。

### 2.4 不建议首版直接播放 PowerPoint

服务端兼容复杂 Office 格式、字体、动画和媒体的成本很高。用户转换为 PDF 可以显著缩小兼容范围，并让播放结果更可预测。

## 3. 系统模块

建议保持单仓库，按以下模块划分：

```text
apps/
├── web/             编辑、主持、参与界面
├── api/             HTTP API 与 WebSocket
└── worker/          PDF、导出、AI 后台任务

packages/            可选的共享类型与 UI
infra/               Docker、Nginx、部署配置
```

后端内部模块：

- `identity`：账号、角色、登录、统一认证适配。
- `presentations`：演示、节点、版本和权限。
- `assets`：PDF、页面图、文件元数据。
- `sessions`：场次、房间码、控制权和当前状态。
- `interactions`：题型配置、答案、聚合和审核。
- `realtime`：连接管理、事件、快照与广播。
- `ai`：模型适配、提示模板、任务和审核。
- `exports`：CSV 和报告。
- `admin`：配置、清理、审计和系统状态。

不同题型共享统一接口，但每种题型的校验、答案结构和聚合逻辑应由独立处理器实现，避免在一个大型条件分支中持续扩张。

## 4. 前端方案

### 4.1 单个前端应用，三种入口

- `/app`：登录后的管理和编辑器。
- `/present/:sessionId`：主持端与演讲者视图。
- `/join/:roomCode`：参与端。

共享组件可以复用题目渲染和结果图表，但主持端与参与端的状态管理必须分开，避免权限动作被错误暴露。

### 4.2 状态分层

- 服务端状态：演示、节点、房间快照、结果，使用查询缓存管理。
- 本地编辑状态：拖动排序、表单草稿、未保存变化。
- 实时状态：WebSocket 事件合并到服务端状态缓存。
- 持久客户端状态：匿名参与令牌和设备侧偏好。

不应让 WebSocket 事件直接任意修改多个组件的本地状态。建议统一经过房间状态存储，并依据事件版本决定是否接收。

### 4.3 PDF 显示

采用混合策略：

1. 上传后后台渲染每页缩略图和演示尺寸页面图。
2. 编辑器列表使用缩略图。
3. 主持播放默认使用页面图，保证浏览器之间一致。
4. 原始 PDF 由 PDF.js 用于高清预览或渲染失败降级。
5. 根据屏幕像素密度选择合适分辨率，避免无意义加载超大图片。

页面图推荐 WebP，同时可保留 PNG/JPEG 兼容输出。具体格式通过实际材料测试决定，尤其要测试细线、公式、图表和小字号文字。

### 4.4 可访问性与投屏

- 参与端表单使用语义化控件和可见焦点。
- 支持键盘操作和足够大的触摸区域。
- 不只用颜色表达选择和状态。
- 投屏图表使用高对比度、大字号和安全边距。
- 对不同宽高比采用 `contain` 布局，禁止拉伸 PDF 页面。

## 5. 后端与 API

### 5.1 HTTP API 职责

适合 HTTP 的操作：

- 用户登录和权限查询。
- 演示 CRUD。
- PDF 上传和处理状态查询。
- 节点编辑和排序。
- 创建与结束场次。
- 提交答案。
- 查询场次快照和历史结果。
- 导出与 AI 任务创建。

答案提交建议通过 HTTP API 完成，并使用幂等键；WebSocket 用于广播状态和聚合结果。相比“所有事情都走 WebSocket”，这种划分更容易鉴权、重试、限流、记录错误和做接口测试。

示例接口边界：

```text
POST   /api/presentations
POST   /api/presentations/{id}/pdf
PATCH  /api/presentations/{id}/nodes
POST   /api/presentations/{id}/sessions
GET    /api/sessions/{id}/snapshot
POST   /api/sessions/{id}/answers
POST   /api/sessions/{id}/commands
POST   /api/sessions/{id}/ai-summaries
GET    /api/sessions/{id}/export.csv
WS     /api/realtime/sessions/{id}
```

具体接口应使用内部不可预测 ID。房间码只用于加入，不作为管理资源的唯一鉴权条件。

### 5.2 命令与事件

主持命令示例：

- `GO_TO_NODE`
- `OPEN_INTERACTION`
- `LOCK_INTERACTION`
- `SET_RESULTS_VISIBILITY`
- `HIDE_RESPONSE`
- `END_SESSION`

服务器校验权限和当前状态后，提交数据库事务，再发布事件：

```json
{
  "event": "session.state_changed",
  "session_id": "...",
  "version": 42,
  "occurred_at": "...",
  "payload": {
    "current_node_id": "...",
    "interaction_state": "accepting",
    "results_visible": false
  }
}
```

版本号必须单调递增。客户端收到旧版本时丢弃；发现版本跳跃时重新获取快照。

### 5.3 答案幂等性

每次提交包含：

- 匿名参与会话 ID。
- 互动节点 ID。
- 客户端生成的请求 ID。
- 答案内容。
- 客户端已知的房间版本。

数据库对 `(session_id, node_id, participant_id)` 建立唯一约束。如果题目允许修改，则更新同一条逻辑答案并记录更新时间；如果不允许，返回已有提交状态。请求 ID 用于处理网络重试。

## 6. 实时通信设计

### 6.1 连接与鉴权

- 主持端使用登录会话和场次控制令牌。
- 参与端先通过房间码换取短期匿名令牌，再建立 Socket.IO 连接。
- 令牌限制到单一场次，并在场次结束后过期。
- WebSocket 建立后立即发送或确认当前快照版本。

### 6.2 服务端权威状态

以下状态由服务端持有：

- 当前节点。
- 场次状态。
- 互动接受状态。
- 结果是否公开。
- 主持控制权所有者。
- 聚合结果版本。

在线人数是近似实时指标，不应与“有效提交人数”混淆。浏览器休眠、网络切换和代理超时会让连接数短暂不准确。

### 6.3 单实例与多实例

MVP 可以只有一个 API 实例并使用 Socket.IO 内置适配器。扩展到多个 API 实例时，使用 Redis Streams Adapter 广播房间事件，使同一房间的主持端和参与端即使连接到不同实例也能收到消息，并支持短暂 Redis 断线后的流恢复。

即使只有一个实例，房间状态接口也不应依赖进程内内存作为唯一来源。Socket.IO 的连接恢复只能作为体验优化；客户端仍必须使用状态版本号和完整快照恢复。

### 6.4 降级

- WebSocket 连接失败时，参与端每数秒获取一次快照。
- 答案仍通过 HTTP 提交。
- 主持端必须明确提示实时通道降级。
- AI、报告或词云布局失败不阻断基本投票和翻页。

## 7. 数据模型

建议的核心关系：

```text
users
  └── presentations
        ├── presentation_assets
        ├── presentation_nodes
        └── presentation_permissions

presentations
  └── live_sessions
        ├── participant_sessions
        ├── answers
        ├── answer_moderation
        ├── result_snapshots（可选）
        ├── ai_summaries
        └── session_events / audit_events
```

### 7.1 关键表建议

`presentations`

- `id`, `owner_id`, `title`, `status`
- `source_asset_id`
- `created_at`, `updated_at`
- `revision`

`presentation_nodes`

- `id`, `presentation_id`, `position`
- `type`
- `config_json`
- `source_page_number`，仅 PDF 页使用
- `created_at`, `updated_at`

`live_sessions`

- `id`, `presentation_id`, `room_code`
- `status`, `current_node_id`
- `interaction_state`, `results_visible`
- `state_version`
- `controller_user_id`
- `started_at`, `ended_at`, `expires_at`

`participant_sessions`

- `id`, `live_session_id`
- `anonymous_token_hash`
- `created_at`, `last_seen_at`
- 不默认保存 IP；安全限流若需要，应使用短期、最小化的信息。

`answers`

- `id`, `live_session_id`, `node_id`, `participant_id`
- `answer_json`
- `is_hidden`
- `created_at`, `updated_at`
- 唯一约束：`live_session_id + node_id + participant_id`

`ai_summaries`

- `id`, `live_session_id`, `node_id` 或数据范围
- `mode`, `status`, `model_info`
- `input_digest`，用于判断输入是否变化
- `draft_text`, `published_text`
- `approved_by`, `approved_at`

### 7.2 JSON 的使用边界

题型配置和不同类型的答案适合使用 JSONB，但公共查询字段必须单独成列。例如节点类型、场次状态、隐藏标记和时间不能全部塞入 JSON。后端还应对每种 JSON 结构执行严格模式校验。

### 7.3 演示版本

已启动场次不应直接引用持续变化的编辑草稿。启动场次时应冻结一份演示修订版本，至少保存节点顺序和配置快照。否则创建者在现场或会后编辑题目会改变历史结果含义。

## 8. PDF 处理

### 8.1 流程

```text
上传临时文件
→ 检查大小、文件签名和基本结构
→ 计算哈希
→ 写入对象存储
→ 创建后台任务
→ 获取页数和页面尺寸
→ 生成缩略图与播放图
→ 可选提取文本
→ 标记资源可用
```

### 8.2 安全隔离

PDF 是不可信输入。渲染进程应：

- 在独立容器或受限用户下运行。
- 限制 CPU、内存、执行时间和临时磁盘。
- 禁止访问不必要的网络和宿主文件。
- 对页数、尺寸、嵌入对象和输出总量设置上限。
- 保持渲染组件的安全更新。

### 8.3 失败与清理

- 任务状态：`queued / processing / ready / failed`。
- 失败时记录对用户可理解的原因和内部错误编号。
- 临时文件定时清理。
- 相同文件哈希可复用转换结果，但必须保证权限隔离。

## 9. 结果聚合

### 9.1 选择题与评分

数据库保存答案明细。提交事务成功后更新 Redis 中的增量聚合，并广播新结果版本。为防止缓存与数据库不一致，应能够从数据库重新计算聚合，并在场次结束时做最终校验。

小规模 MVP 也可以每次按节点在数据库聚合，但必须用突发并发测试验证。不要在每个新答案到来时把全部答案拉到应用进程中重新统计。

### 9.2 文本与词云

- 原始回答持久化。
- 归一化结果与原始文本分开保存。
- 隐藏状态改变后重新计算公开结果。
- 词云坐标布局可以在主持端计算；服务端只广播词频，降低服务端渲染压力。

## 10. AI 方案

### 10.1 服务边界

建立内部 AI 网关接口，不让业务模块直接绑定某个模型供应商：

```text
summarize(input, mode, policy) -> draft
suggest_questions(pdf_text, context) -> suggestions
```

适配器可连接所内模型或允许的外部服务。所有调用通过后台任务完成，设置超时、重试次数和并发上限。

### 10.2 数据最小化

- 只发送当前总结需要的回答，不发送完整用户资料。
- 排除主持人已隐藏的回答。
- 如内容可能涉密，默认禁用外部 AI。
- 记录模型标识、输入范围摘要和生成时间，但日志不保存完整提示及答案正文。
- AI 结果保留“草稿”和“已发布”两个版本。

### 10.3 输出可靠性

- 提示模型只总结提供的数据，不补充外部事实。
- 结果中显示样本数量和数据范围。
- 主持人确认后发布。
- 输入答案变化后标记已有总结可能过期。
- 模型服务失败时允许重试或人工总结，不影响演示。

## 11. 身份、安全和隐私

### 11.1 管理端认证

如果所内已有 OIDC、CAS 或 LDAP，正式版本应接入统一认证。MVP 本地账号应采用安全密码哈希、短期会话、CSRF 防护和管理员重置流程，不自行设计密码加密算法。

### 11.2 参与端匿名机制

1. 参与者提交房间码。
2. 服务器检查场次、速率和过期时间。
3. 服务器签发限制到该场次的随机匿名令牌。
4. 浏览器本地保存令牌以便刷新恢复。
5. 数据库只保存令牌哈希或不可反推的标识。

匿名不能等同于无限提交。系统仍可以按匿名会话、房间和短期网络信号做频率限制，但不应构建设备指纹或长期追踪参与者。

### 11.3 房间码

- 使用去除易混淆字符的随机码。
- 不采用可推测的自增编号。
- 设置有效期和失败尝试限流。
- 房间码只能加入参与端，不能授予主持权限或查看后台明细。

### 11.4 常规 Web 安全

- HTTPS、Secure/HttpOnly/SameSite Cookie。
- 严格的资源所有权校验。
- 输入长度、结构和内容校验。
- HTML 转义与内容安全策略，尤其是开放文本和 AI 输出。
- 上传下载使用短期授权链接或经鉴权接口。
- 数据导出防止公式注入，对以 `=`, `+`, `-`, `@` 开头的单元格做安全处理。
- 对登录、加入房间、提交答案、AI 任务和导出分别限流。
- 依赖漏洞检查、备份恢复演练和审计日志。

## 12. 部署方案

### 12.1 MVP 部署

一台所内服务器或虚拟机运行：

```text
docker compose
├── nginx
├── web
├── api
├── worker
├── postgres
├── redis
└── minio（也可先使用受备份的挂载卷）
```

优点：部署简单、数据路径清楚、容易备份和迁移。风险是单机故障会导致服务不可用，因此正式重要活动前应做资源监控、定期备份和恢复演练。

### 12.2 正式部署增强

- PostgreSQL 使用独立受管实例或主备机制。
- 文件存储独立并纳入备份。
- API 可运行多个实例，由 Nginx 负载均衡。
- Redis 用于跨实例实时广播。
- Worker 单独设置 CPU/内存限制，避免 PDF 处理影响现场 API。
- 将现场访问域名、证书和内网 DNS 纳入所内基础设施。

除非已有统一 Kubernetes 平台和运维能力，否则不因本项目单独引入 Kubernetes。

### 12.3 容量估算方法

部署前用真实材料测量：

- 平均 PDF 大小与平均页数。
- 每页缩略图和播放图大小。
- 演示保留数量。
- 单场回答数与文本平均长度。
- 最大并发连接和短时提交峰值。

粗略存储公式：

```text
总存储 ≈ 原始 PDF
       + 页数 ×（缩略图 + 播放图）
       + 答案与导出文件
       + 备份副本
```

页面图往往比结构化答案占用更多空间，因此需要重点监控资源转换后的放大系数。

## 13. 可观测性与运维

### 13.1 指标

- 当前活跃房间数。
- WebSocket 在线连接数和重连率。
- 翻页事件到达延迟。
- 答案提交吞吐、失败率和 P95 延迟。
- PDF 任务队列长度、耗时与失败率。
- AI 任务耗时、失败率和调用量。
- 数据库连接、慢查询和存储使用量。

### 13.2 日志

日志采用结构化格式，包含请求 ID、场次 ID、事件类型和错误码。避免记录：

- 登录令牌。
- 完整文本答案。
- 完整 AI 输入。
- PDF 内容。
- 无必要的 IP 和设备信息。

### 13.3 备份

- PostgreSQL 定期备份并验证恢复。
- 对象存储按相同时间点或版本策略备份。
- 记录应用版本与数据库迁移版本。
- 升级前执行可恢复备份。

## 14. 测试策略

### 14.1 单元测试

- 题型配置校验。
- 答案合法性和幂等性。
- 聚合计算。
- 状态机转换。
- 房间码和匿名令牌。
- 数据保留与清理规则。

### 14.2 集成测试

- 上传 PDF 到页面资源完成。
- 创建场次、加入、提交和导出。
- 数据库事务与 Redis 广播。
- Worker 失败、超时和重试。
- AI 关闭、失败及草稿审核。

### 14.3 端到端测试

- 编辑端创建完整演示。
- 主持翻页，多个参与端同步。
- 锁题、公开结果、隐藏文本。
- 浏览器刷新和断线重连。
- 场次结束和历史结果查看。

### 14.4 负载与故障测试

重点模拟“集中提交”，而不是只测均匀请求：

- 100、300 个参与者在 5—10 秒内提交。
- 主持人同时翻页和切换结果显示。
- API 单实例重启。
- Redis 短暂不可用。
- Worker 处理异常 PDF。
- 数据库短时变慢。
- 手机从 Wi-Fi 切换到移动网络后重连。

## 15. 主要技术风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 复杂 PDF 渲染不一致 | 页面错位、字体或公式显示异常 | 后台统一渲染页面图，PDF.js 作为补充；用真实材料建立兼容测试集。 |
| 现场集中提交 | 延迟上升或统计错误 | 幂等提交、唯一约束、增量聚合、突发负载测试。 |
| WebSocket 断连与事件乱序 | 参与端显示错误题目 | 服务端版本号、状态快照、自动重连和轮询降级。 |
| 匿名文本滥用 | 投屏出现不适当内容 | 限流、敏感词、主持审核、隐藏后排除 AI。 |
| AI 泄露或错误总结 | 数据合规和现场误导 | 可关闭外部 AI、数据最小化、异步草稿、人工确认。 |
| 编辑内容影响历史场次 | 历史数据失去语义 | 启动场次时冻结演示修订。 |
| 单机部署故障 | 现场不可用 | 监控、备份、预加载、备用主持；重要程度提升后拆分数据库和存储。 |
| 过早复杂化架构 | 开发和运维负担过高 | 模块化单体、明确边界，依据测量结果再扩容。 |

## 16. 实施顺序建议

### 里程碑 1：技术骨架

- 账号、数据库迁移、文件存储。
- PDF 上传、后台处理、页面预览。
- 演示与节点数据模型。

### 里程碑 2：编辑与播放

- 节点编辑器。
- PDF 全屏播放。
- 演示修订和场次创建。

### 里程碑 3：实时闭环

- 房间码、匿名参与。
- WebSocket、快照和重连。
- 单选、多选、开放问答。
- 主持状态控制和实时结果。

### 里程碑 4：可靠性与管理

- 审核、限流、审计、导出。
- 负载测试、故障恢复和监控。
- 数据保留与后台清理。

### 里程碑 5：增强互动与 AI

- 评分和词云。
- AI 总结草稿与审批。
- 会后报告和题目推荐。

## 17. 开发前建议验证的原型

在完整开发前，建议先做三个相互独立的小型验证：

1. **PDF 兼容验证**：收集所内 20—30 份有代表性的 PDF，比较后台页面图和 PDF.js 的清晰度、耗时与文件大小。
2. **实时并发验证**：用最小房间服务模拟 300 个连接和集中提交，验证 WebSocket、数据库与 Redis 路径。
3. **手机可用性验证**：在实际会议室网络中测试扫码、微信内置浏览器、刷新恢复和投屏延迟。

这三个验证可以在界面尚不完整时尽早暴露主要风险。

## 18. 最终推荐

首版以 React + Vite、NestJS、Socket.IO、PostgreSQL + Prisma、Redis + BullMQ、MinIO 和独立 Worker 构成 TypeScript 模块化单体；使用 Docker Compose 在所内部署。PDF 采用后台页面图为主、PDF.js 为辅，Worker 调用 MuPDF 或 Poppler；答案通过带幂等键的 HTTP API 提交，房间状态和结果通过 Socket.IO 推送；PostgreSQL 保存权威数据，Redis 承担任务队列、缓存和跨实例广播。

应把开发资源首先投入到 PDF 兼容、房间状态机、断线恢复、集中提交和文本审核。AI 总结通过可替换适配器异步加入，并默认先形成主持人草稿。所有前后端数据和实时事件必须通过共享 Schema 或生成契约约束，数据库迁移、状态转换和关键事件必须进入自动化测试。该路线能够在不过度设计的前提下覆盖首版需求，也保留后续扩展到更多互动类型、统一身份认证和多实例部署的空间。
